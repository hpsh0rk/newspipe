# Reliability Follow-up Implementation Plan

> For agentic workers: execute inline with superpowers:executing-plans and test-driven-development. Commit each verified stage separately.

**Goal:** Fix the six reproduced residual defects before changing the user interface.

**Architecture:** Keep the CLI as the only write boundary, preserve YAML/JSONL compatibility, and distinguish accepted work from completed work. Scheduler completion is per source. Listener configuration must describe what is actually running, not just what is on disk.

**Tech Stack:** Python 3.11+, standard library, PyYAML, unittest.

**Spec:** Confirmed reproductions in the handoff and AGENTS.md hard rules. Frontend scope is pending confirmation and is not part of this implementation plan.

## Global Constraints

- Use temporary state and mocked transports; never send real cards or start real IM connections.
- Preserve result envelopes, favorite receipts, single-WS ownership, and last-known-good configuration.
- Manual edits use apply_patch. Each stage runs the complete offline suite and secret scanner before commit.
- Do not introduce host imports, a second Web write path, or a database migration.

## Review Focus

- Human, JSON and legacy probes must execute once in the selected directory.
- Partial slot failures must retry only unfinished sources and stop within bounded attempts/window.
- Listener reconfiguration failures must not masquerade as effective settings or overlap WS clients.
- Long text and whitespace must survive translation chunking; empty translated blocks must not pass completeness checks.
- Completed callback IDs must deduplicate after restart and migration without rescanning terminal payload history every tick.

## Decisions and Verification

Ruling: Listener resource changes are restart-required rather than hot-swapped. Stopping a working listener to try unverified credentials/ports adds an avoidable ingress outage and makes the one-WS guarantee harder to prove. Business settings and hooks still reload live; restart-required fields must be explicitly visible in status.

Ruling: Frontend design waits for the notification ownership decision. Existing single-target behavior is evidence of the current model, not proof that the user wants to keep it.

Stage 1 verification: 411 offline tests passed; scanner clean (121 files). Regressions first failed with two probes, default-directory leakage and zero exit codes for failed service runs, then passed after the shared execution/formatting fix.

Stage 2 verification: 416 offline tests passed; scanner clean. Slot scheduling is serialized, attempts are persisted before execution, and successes are recorded per source. Configuration-missing results remain incomplete and wait for a configuration change rather than retrying unchanged input. Existing completed-slot records remain valid; new progress retains only 14 days.

Stage 3 verification: 421 offline tests passed. Startup failures propagate nonzero status; listener/resource changes retain effective settings and produce restart-required status. The Web contract and selected-directory CLI status expose the same runtime record. Review found the WS handle lost asynchronous failures and only acquired its constructed client after the blocking call; new RED/GREEN tests cover immediate client ownership and failure visibility. Runtime status is explicitly a last observation, not a liveness proof.

Stage 4 verification: 424 offline tests passed; scanner clean. Chunk concatenation reproduces punctuation-free long input and whitespace exactly; each chunk remains bounded. Blank/non-string translated blocks return incomplete rather than a false success.
